Most medical education tools evaluate whether the student got the diagnosis right.

MedCoach evaluates how they thought.
I built an AI Clinical Reasoning Tutor where medical students practice diagnosing virtual patients through realistic clinical encounters.

How it works:
→ Generate a patient case
An LLM creates a unique patient with history, symptoms, vitals, and a hidden diagnosis.

→ Interview the patient
Students ask questions naturally.
The Patient Agent only reveals information that was actually asked and stays consistent throughout the encounter.

→ Submit diagnosis + reasoning
Students explain both the diagnosis and their clinical thinking.

→ Get evaluated
The Evaluator Agent scores the entire process (out of 10), including:
• question quality
• missed history
• reasoning gaps
• cognitive bias
• dangerous assumptions
• actionable feedback

→ Learn
The Teacher Agent explains the disease, highlights missed signals, and shows a stronger diagnostic approach.

Architecture (LangGraph):
START → Evaluator → Teacher → Memory (SQLite) → END

Interactive patient conversations run outside the graph for responsiveness.
Stack:
• Frontend — Streamlit
• Backend — Python
• Orchestration — LangGraph
• Storage — SQLite
• Streaming responses

This is V1 — focused on simulated patient reasoning.
V2 will introduce richer clinical workflows, external knowledge retrieval, and stronger diagnostic support.

Open to feedback from people building in MedEd, AI, and simulation systems.

Most RAG projects look good until you ask a real question.

I wanted to go beyond a basic demo and understand what it actually takes to build a retrieval system that works on legal documents. So I built a Legal RAG System using the IPC, the Constitution of India, and case law documents.

What stood out to me while building this is that retrieval quality depends far more on document structure than I initially thought.

A model can only answer well if the right chunks are retrieved first.
And that only happens when the ingestion pipeline is designed properly.

While working on this project, I had to rethink the pipeline from the ground up:
- statutes had to be chunked by section
- the Constitution had to be chunked by article
- judgments had to be chunked by paragraph blocks
- metadata had to support exact references like Section 302 IPC or Article 21
- the answer layer had to be constrained enough to avoid hallucinated responses

This project taught me a lot about:
- why generic chunking often fails on legal documents
- how retrieval errors happen long before the LLM generates an answer
- how important metadata design is for precision
- how to build a more grounded and reliable legal Q&A pipeline

Tech stack:
Python, PyPDF, LangChain, OpenAI Embeddings, ChromaDB, and Groq

🚀 This Week: Shipped a Production-Grade Async Web Scraping System
Problem
Extract structured article data from a large paginated blog (170+ pages, 3,400+ articles) — without getting blocked, crashing mid-run, or losing data.
What the System Does
• Discovers article URLs across pagination
• Fetches pages asynchronously using aiohttp
• Controls concurrency using semaphores
• Applies rate limiting to avoid bans
• Handles failures safely (timeouts, bad responses, partial data)
• Logs per-URL start time, end time, and duration
• Processes data in fixed-size batches
• Saves each batch incrementally (crash-safe persistence)
Results
✅ 3,400+ articles scraped
✅ Zero crashes during full run
✅ No IP bans or rate-limit lockouts
✅ Each batch persisted independently
✅ Full pipeline completed safely (even tested on a mobile hotspot)
Key System Design Decisions
• Batch-based persistence → prevents total data loss
• Structured logging → makes debugging and monitoring easy
• Async + controlled concurrency → fast and safe
• Fail-safe networking → retries + timeout handling
